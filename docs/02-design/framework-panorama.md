## 1. 目标与边界 🟡

**一句话**：输入一件赌博类治安案件的案情，引擎给出依法可能的处罚**分布**（不只是一个数），并说明依据、类案和每个情节的影响，供办案人员参考。

**输出五项**（方案 §1）：

| 输出 | 例子 |
|---|---|
| 定性 | 不构成违法 / 参与赌博 / 为赌博提供条件 / 涉嫌犯罪、建议移送 |
| 情节档次与修正 | 一般档 / 情节严重档；从轻、减轻、从重、不予处罚、不执行拘留 |
| 处罚分布与区间 | 拘留 10 日的概率 0.52……；90% 预测集 `[[5,5],[10,12]]` |
| 依据 | 只引用规范库里逐字核对过、行为时有效的条文，再加类案 |
| 解释 | 每个情节的影响、缺了哪些事实、拟处罚偏离预测多少 |

**边界**：
- **v1 只做行政**（治安管理处罚）和"是否涉嫌犯罪、需移送"的识别；刑事量刑留到 v2，CAIL 刑事数据只当锚点和先验用。
- **定位是辅助**：要素先由人确认，结论始终带区间和不确定性，并显著提示"仅供参考"（法发〔2022〕33 号）。
- **两个"不"**：不写"赌资大于 X 就拘留 Y 天"这类手写打分规则；也不让大模型直接生成处罚数字（方案 §2.3）。

### 2.1 一条主线：一件案子怎么走完引擎（示例） 🟡

> 案情：2026 年 3 月，甲在自家组织麻将，每局抽台费 20 元，共抽头 800 元，现场查获赌资 3,000 元；甲 2025 年 8 月曾因赌博被拘留 5 日。

| 步骤 | 模块 | 做什么 | 这件案子的结果 |
|---|---|---|---|
| 1 | M1 | 从原文抽要素，每个值附原文证据 | 行为类型＝为赌博提供条件；抽头＝800 元（证据："每局抽取台费 20 元……共计 800 元"）；现场赌资＝3,000 元；前次处罚日期＝2025-08 |
| 2 | 人工 | 办案人员确认或修改要素 | 确认 |
| 3 | M2 | 按行为时、决定时选法律版本；算合法空间 Ω；看修正情节；查刑事门槛 | 行为在 2026 年 → 新法第八十二条；一年内受过处罚 → 从重；抽头 800 元，远低于聚众赌博入罪的 5,000 元 → 不提示移送；Ω＝{罚款 ≤1,000 元，拘留 1–5 日，拘留 10–15 日并处罚款 1,000–5,000 元} |
| 4 | M3 | 只在定性有疑问时调用 | 抽头明确，营利目的清楚 → 不调用 |
| 5 | M5 | 找相似案件 | 同省、新法、为赌博提供条件、抽头数百元的 10 个案例及其处罚分布 |
| 6 | M4 | 四个专家各自给分布，融合、套上 Ω、校准、给区间 | 情节严重档 0.69；拘留 10 日 0.52、12 日 0.15……；90% 预测集 `[[10,12]]` |
| 7 | M6 | 解释、追问、说理并校验 | "去掉抽头后，情节严重档概率从 0.69 降到 0.25"；说理里引用的第八十二条与规范库逐字一致 |
| 8 | 输出 | 卡片 + 审计记录 | 记录引擎版本、规范库版本、输入哈希，保证可复现 |

**关键设计点**（每一处都对应一个"不交给大模型"的决定）：
- 法律版本、合法空间、人均赌资这类计算由代码完成（M2）；
- 处罚数字由校准过的统计模型给出（M4）；
- 大模型只负责读懂原文（M1）、做少数开放性辨析（M3）和写说理（M6），而且写完要过校验器。

### 4.3 数据最大的三个缺口（引擎视角）

1. **信息完整度 40%**：很多文书只写"因赌博"，没有金额与情节，模型学不到东西（CAIL 的教训）。
2. **新法案件少**：2026 年后的行为只有 7 件，T-time 测试集要 50 件。
3. **不予处罚只有 2 件**：门禁 G3.2 要求这一类单独达标。

### 4.4 统一中间格式 parsed-1 详解 🟡

**它是什么**：各来源解析器的**共同输出格式**。不管原文来自网页、法宝还是裁判文书，解析完都写成同一种记录，一份文书里的一个当事人一条。之后的脱敏、隐私扫描、去重、事件分组、分级只实现一次（L2 构建），交付层（L3）就是它脱敏、冻结后的样子。

**"已确立"到什么程度**：

| 层面 | 状态 |
|---|---|
| 字段定义 | ✅ 写成代码：`justilaw-api/app/discretion/records.py`，规格 §7 的字段总表由代码生成，测试保证两者一致 |
| 自检与验收 | ✅ 解析层自检 `records check --layer parsed`；交付层验收 `accept_delivery.py` |
| 交付层（L3）实际产出 | ✅ 发现层的首批交付基本符合，验收"部分通过" |
| 解析层（L1）实际产出 | ❌ 三个来源都还没有按 parsed-1 输出（网页的解析产物差的主要是搬字段，见规格 §6） |

**容易混淆的一点：网页端交付的是"交付层"文件，不是"中间格式"文件。**

| 文件 | 属于哪一层 | 是否符合契约 |
|---|---|---|
| `admin/web_cases.pre_deid.jsonl`（4,906 条，网页解析器的输出） | 本应是 L1 解析层（parsed-1） | ❌ 不符合：4,906 条全部有 error，主要是缺新字段（格式版本、来源、批次、解析器版本、`quality` 结构），另有 6 类数据问题 |
| `admin/admin_cases.schema-1.0.0.jsonl`（881 件） | L3 交付层 | ✅ 基本符合：验收"部分通过"，869 件可用 |

原因是时间先后：发现层的构建脚本 `build.py` 在 parsed-1 定义之前（14:43）就已经从自己的解析格式**直接**做出了交付层，跳过了中间格式。只有网页一个来源时这样能用；要把法宝、裁判文书合并进同一次构建，各来源就必须先输出 parsed-1。

**九组字段**（`字段名` 解析层 / 交付层）：

| 组 | 字段 | 作用 | 谁来填 |
|---|---|---|---|
| ① 身份与溯源 | `record_version`、`id`、`source`、`batch`、`parser`、`source_type`、`source_ref`、`doc_no` / 交付层只留 `id`、`source_type`、`doc_no_hash` | 每条记录能追到原文、原始批次和解析器版本；交付层只能经台账反查（D3） | 解析器 |
| ② 时间、地点、法律 | `behavior_date`、`decision_date`、`authority`、`region`、`province`、`law_version` | M2 选法律版本和省级基准；`law_version` 是**实际适用**的版本（D8） | 解析器；`region` 由构建补全 |
| ③ 正文与分段 | `text_full`；`text_facts`、`text_evidence`、`text_reasoning`、`text_decision`、`text_review`；交付层加 `segments`（起止位置）、`text_sha256` | "题目"和"答案"分开：事实段是模型输入，理由段和决定段不能进输入；正文冻结后，证据偏移才稳定 | 解析器切分；构建算偏移和哈希 |
| ④ 当事人 | 解析层 `subject_mention`（本人原写法）/ 交付层 `subject_alias`＝"甲" | M1 只抽本人的要素；多人案件要能指认本人 | 解析器；构建替换为"甲" |
| ⑤ 处罚结果 | `outcome`：`type`、`detention_days`、`fine`、`detention_not_executed`、`confiscation`、`articles`、`stated_circumstances`、`law_version` | M4 的**标签** | 解析器 |
| ⑥ 复核结论 | `review`：`result`（维持 / 变更 / 撤销 / 确认违法 / 程序驳回 / 无）、`changed_outcome` | 被撤销或变更的处罚不能当正确答案 | 解析器 |
| ⑦ 质量与分级 | `quality`：`tier`（L1 金标候选 / L2 只有结果 / L3 范围外 / L4 待核）、`in_scope`、`completeness{has_amount, has_outcome}`、`parse_warnings`、`form`、`ocr`、`facts_contains_conclusion` 等 | 构建按分级分流；校正时知道重点看哪里 | 解析器；构建补充 |
| ⑧ 事件 | 解析层 `event_key`（指纹）/ 交付层 `event_id`、`linked_ids` | 同一事件的多人不能分到训练集和测试集两边（门禁 G1.3、R7） | 解析器给指纹，构建生成编号 |
| ⑨ 其他 | 解析层 `extra`（页面编号、站点、法宝引证码等） | 来源专有字段集中放，交付层一律不出现 | 解析器 |

**从 L1 到 L3，构建做了什么**：
1. 脱敏：本人替换为"甲"，其他人编为乙、丙、丁；删除证件号、住址、电话；年龄写成"行为时××周岁"；正文日期只保留到月。
2. 隐私扫描（R6）。
3. 冻结正本，算 `segments` 和 `text_sha256`。
4. 文号换成 `doc_no_hash`。
5. 去重，生成 `event_id`、`linked_ids`。
6. 按分级拆成主文件（L1）和只有结果的文件（L2），删除内部字段。

### 4.4.1 构建细节：冻结正文、几种哈希、事件分组、删掉的字段 🟡

依据发现层的实际代码 `research/discretion/harvest/build.py`、`deid.py`（harvest-0.4）。

**(1) 冻结正文**：脱敏后的 `text_full` 定为"正本"，之后不再改动，连纠正一个 OCR 错字也不行；要改就出新版本，并重做受影响的标注。

为什么必须冻结：下游所有东西都用"第几个字到第几个字"来指向正文：
- 交付层的 `segments`，例如事实段 `[38, 77]`；
- D1 标注里每个要素的证据 `{quote, start, end}`；
- 脱敏映射 `deid_map`；
- 前端高亮证据，M6 核对"每个事实都有原文依据"。

正文只要在前面多一个字或少一个字，后面所有位置都会错一位。比如证据本来高亮"赌资3000元"，错位后变成"资3000元，"。

**脱敏为什么还能保住位置**：替换会改变长度，例如"张绍刚"换成"甲"少了 2 个字。`deidentify()` 记下每一处替换，`project()` 再把"原文第 n 个字"换算成"脱敏后第 m 个字"，所以各段的位置是在正本上重新算出来的，验收时逐条核对切出来的文字与各段一致。

**(2) 四种"哈希"或编号，各管一件事**：

| 名字 | 对什么算 | 管什么 | 不管什么 |
|---|---|---|---|
| `text_sha256` | 每条记录的脱敏正本 | ① **把标注绑定到正本**：D1 标注记下所对应的哈希，正文一变即可发现，标注作废而不是悄悄错位；② **重建时只重标变了的记录**：发现层今天把交付重建了一次（955 → 881），哈希没变的记录，标注可以直接沿用；③ **复现与审计**（红线 R8）：模型用的是哪一版数据，逐条可查；④ **封存测试集**（门禁 §7）：测试集封存后谁改了一个字都会被发现；⑤ **缓存**：M1 抽取结果按哈希缓存，正文没变就不用重跑（省算力或 API 费）；⑥ 顺带能发现完全相同的正文 | **近重复**：只差一个字，哈希就完全不同，所以不能拿它去找近重复 |
| `doc_no_hash` | 每条记录的文号，先规范化（去空白、统一括号）再取 SHA-256 前 16 位 | ① **精确去重**：同一文号只留一份，按"文书类型 > 是否切分 > 事实段长度 > 非扫描件"挑最好的那份（主文件因此去掉 94 份）；② **关联**：复议书里引用的原处罚文号也取哈希，与原处罚决定书对上 | 不能反推出原文号（隐私） |
| `SHA256SUMS` | 整个交付文件 | **整批是否被改过**：验收发现"发布后又被改写"就判"不通过" | 不知道是哪条变了（那要看 `text_sha256`） |
| `event_id` | **同一事件成员的编号列表**（`"E-" + sha1(排好序的成员 id)` 前 10 位） | 划分训练集和测试集时**整组放在同一侧**（门禁 G1.3、红线 R7） | 它不是正文的哈希 |

**(3) 事件是怎么归并的**（`dedupe_and_link`，并查集：只要两条之间有一条连线，它们就是同一事件，可以传递）：
1. **近重复**：事实段加决定段，按 5 个字一组切片，重合度（Jaccard）≥ 0.8，且行为日期相差不超过 31 天，就连起来。**近重复不删，只归为同一事件**；日期相差一个多月的，是套话相同的不同案件，不连；
2. **多人同案**：同一站点、同一行为日期，事实段按 3 个字一组切片的重合度 ≥ 0.5，就连起来；
3. **复议 ↔ 原处罚**：复议书引用的原处罚文号哈希，与某份决定书的 `doc_no_hash` 相同，就连起来，并写入双方的 `linked_ids`。

主文件 881 件归并为 407 个事件，其中 143 个事件有多条记录。

**(4) 删掉、搬走、新增的字段**（网页解析产物 → 交付层）：

| 处理 | 字段 | 为什么 |
|---|---|---|
| **删掉** | `source_ref`（原网址）、`site`（站点域名）、`page_id`（收割页编号）、`title`（网页标题，常含"王××赌博案"和文号）、`publisher`（发布单位）、`doc_no`（原文号）、`item_index`（汇总页里第几条）、`gambling`、`in_scope`（筛选标记，交付的都是"是"）、`needs_ocr`、`attachment_files`（收割状态） | 前五项加原文号**都能直接搜回未脱敏的原网页**。删掉以后，交付文件本身无法还原身份，溯源只能经由仓库外的台账 `manifest_web.csv`（D3）。其余是流水线内部状态，引擎不需要 |
| **搬进 `quality`** | `ocr`、`completeness`、`parse_warnings`；`outcome.detention_items`（合并执行前各项拘留天数）、`outcome.from_execution_clause`（结果是否从"执行方式"一句兜底取得） | 解析过程的信息，用于提示人工校正时重点看哪里，不属于标签 |
| **构建中临时使用、写出前去掉** | `_cited`（复议引用的原处罚文号哈希，用来关联）、`_site`（用来匹配区划、做"同站同日"分组） | 以下划线开头的键在写出时一律去掉 |
| **新增** | `doc_no_hash`、`subject_alias`、`event_id`、`linked_ids`、`r6_scan`、`region`、`region_level`、`province`、`province_code`、`segments`、`text_sha256`、`schema_version`、`pipeline_version`；`quality` 里新增 `ambiguous_persons`、`age_uncertain`、`subject_variants`、`persons`、`deid_counts`、`r6_soft` | 交付契约要求的字段 |
| **单独存放** | `deid_map.jsonl`：每处人名替换的"代号 → 原文位置、长度"，**不含原名** | 复核脱敏时用，不进交付文件 |

**代码里发现的问题**：`law_version_of()` 按行为日期（2026-01 为界）判定顶层 `law_version`，覆盖了解析器按引用法条得出的版本。这就是验收中那 13 条"法律版本前后不一致"的来源，应改为以 `outcome.law_version`（按引用法条）为准（D8）。

### 4.7 分段是怎么做的（网页链路的实际实现，`research/discretion/harvest/parse.py`） 🟡

分段全靠**正则匹配文书里的固定用语**，按页面形态走五条规则。先用 `canonical()` 去掉网页导航和页脚：正文从第一个当事人行（"违法行为人：张××"或"张××，男，"）开始，往前带上机关名、文书名、文号行。

| 形态 | 识别 | 事实段从哪到哪 | 其他段 |
|---|---|---|---|
| **叙述式处罚决定书**（`segment_decision`） | 默认形态 | 从"现查明 / 经查明 / 经查实 / 经查"之后，到以下三者中最早出现的一个：证据句（"以上事实有……证实 / 为证"）、"本局认为 / 综上"、决定句（"根据《……》……之规定，现决定"） | 证据段＝那一句；理由段＝"本局认为"到决定句；决定段＝决定句到"执行方式 / 如不服"（找不到就取 400 字）。找不到"现查明"或决定句的，整篇标"未切分" |
| **字段式公示**（`field_values`） | 有"违法事实""处罚事由""处罚结果"等字段标签 | "违法事实 / 处罚事由"字段的值；**没有这个字段时退而取"案件名称"那一行**（如"张某赌博案"） | 决定段＝依据、结果、种类、罚款金额几个字段**用"；"拼起来**（所以不是原文子串，解析层自检的 149 条"决定段不是正文子串"主要来自这里，构建时已重新定位） |
| **汇总页**（`split_items`，红塔式） | 一页多条"违法行为人××，因……，于……给予……的处罚" | 每条里第一个"被"字之前的部分 | 决定段＝"根据"之后 |
| **结果表**（`table_rows`） | 标题含"处罚结果 / 公示表" | 整行既当事实又当决定，标"未切分" | — |
| **复议决定书**（`segment_review`） | 标题或正文有复议特征且有"被申请人" | "经审理查明 / 本机关查明"到"本机关认为" | 复核段＝"本机关认为"到"决定如下"后 300 字；从"……行罚决字……"句取原处罚 |

**实测暴露的三个问题**：
1. **当事人段不归任何一段**：叙述式里"现查明"之前的"甲，女，58 岁，行为时 57 周岁"（以及"违法经历"）不在事实段里，模型读不到。→ §4.5 提议新增 `text_party`。
2. **情节常常只出现在决定段的法条里**：例如事实段没写主动投案，决定段却引用"第二十条第（四）项"。对 M1 来说这个情节"读不到"（事实段里没有证据）；对 M4 来说，它可以作为**由法条反推的情节特征**（`feature_source = 法条反推`），不算泄露答案，因为情节本身是事实，处罚才是答案。
3. **汇总条目混进主文件**：纳入标准②只要求事实段 ≥ 30 字，红塔式"违法行为人甲，于 2026 年 6 月因实施为赌博提供条件、赌博的违法行为，"（34 字）就够了，但其中没有任何要素。→ 应按形态而不是字数判断，汇总条目一律进只有结果的文件。

### 4.9 "验收通过"离"可以训练"还有多远 🟡

**验收通过 ≠ 内容够用**。验收查的是"安全、合规、格式对"：已脱敏、隐私扫描为零、位置与哈希一致、处罚在法定范围内、字段符合契约。它**不查**文书里写没写模型需要的信息。所以"869 件可以进入标注"的意思是：这些记录可以安全地交给人看、交给模型读，标出来的东西不会因为格式或位置问题作废。内容上仍有 §4.5 的三个缺口和问题清单 I-01 至 I-03。

**`pilot50` 不是预标注，也不是训练集**：它是从交付里分层抽出的 50 件**空白样本**，用来做门禁 G0.3 的**双人试标**：两个人各自独立按标注指南标，算一致性（分类字段 Cohen's κ ≥ 0.80，数值字段完全一致率 ≥ 95%）。目的是检验**标注指南本身**是否清楚，不达标就改指南重试，最多两轮。标完的 50 件会成为最早的金标，但 50 件远不够训练。

**数量要求从哪里来**：

| 要求 | 数量 | 出处 | 含义 |
|---|---|---|---|
| 行政案例金标总量 | ≥ 500 件，其中目标省 ≥ 300 件 | 门禁 G1.1 | 训练、验证、测试**合计**的人工校正件数 |
| 行政测试集 T-admin | ≥ 150 件 | G1.1 | 从金标里先划出并封存，不参与训练 |
| 时间外推测试集 T-time | ≥ 50 件（2026 年后的行为） | G1.1 | 同上 |
| 双人标注比例 | 金标的 ≥ 20%（约 100 件），κ ≥ 0.80 | G1.2 | 估计标注质量 |
| 抽取器微调需要的金标 | 300–500 件 | 引擎方案 §6 | 再加上全部数据的银标 |
| 裁量模型：每个目标省 | ≥ 300 件行政案例 | 引擎方案 §6 | 处罚标签交付层已有，不用人工标；要人工的是要素（特征） |

所以 500 是**金标总数**，扣除两个测试集（约 200 件）后，真正参与训练和验证的金标约 300 件；其余数据靠银标补充训练量（银标只进训练，绝不进测试）。

**现在的家底**（验收通过的 869 件）：

| 统计 | 数量 | 对照要求 |
|---|---|---|
| 记录 / **独立事件** | 869 / **397** | 同一事件的多人高度相似，按事件划分后，有效样本更接近 397 |
| 有金额且不是汇总公示 | 257 条 / 152 个事件 | 信息足够、标注最有价值的部分 |
| 候选目标六省（山西、上海、浙江、安徽、湖南、云南） | 155 条 / 85 个事件 | 目标省 ≥ 300：**差得最远**；河北 + 广西就有 644 条 |
| 2026 年后的行为 | 7 | T-time ≥ 50 |
| 不予处罚 | 2 | G3.2 要求这一类 F1 ≥ 0.80 单独达标 |

**结论**：总件数上，500 件金标的原料是够的；**卡住的是结构**：目标省分布、新法案件、不予处罚、信息完整度。目标省如果改成河北、广西，或者把河北纳入，第一个缺口会大幅缓解（总览 §7 第 5 项）。

**从现在到"可以训练"的顺序**（门禁不过不进下一阶段）：
1. **P0 收尾**：pilot50 双人试标，κ 达标（G0.3）；选定教师模型 B1（G0.5）；规范库与黄金用例签字（G0.1、G0.2）。
2. **P1 数据**：B1 在全部可用记录上打银标 → 先划出并封存 T-admin、T-time → 按"随机抽样 + 模型最不确定"挑案例人工校正，直到金标 ≥ 500 → 20% 双人标注 → 数据卡 → 冻结基线 B0–B9 跑一遍写入排行榜（G1.1–G1.6）。
3. **P2 抽取器**：用"银标 + 金标"训练 M1（LoRA），在 T-admin 上考核（G2.1–G2.12）。
4. **P3 裁量**：D2 训练表（金标要素或 M1 预测的要素 + M2 推导量 + 交付层标签）训练 M4（G3.x）。M4 的原型可以提前用银标特征搭起来，但正式考核要等 P1 封存的测试集。

**要从这里走到 D1、D2，还差四步**：
1. **定输入范围**：加 `text_party` 段（§4.5），这样年龄、违法经历才能进入模型输入；
2. **选教师模型 B1**（门禁 G0.5），在 869 件上打**银标**，附抽取理由；
3. **双人试标 pilot50**（G0.3，κ ≥ 0.80），据此修订标注指南；然后按"随机抽样 + 学生最不确定的"挑案例做人工校正，得到**金标**；
4. **拼 D2**：金标（或银标、或 M1 预测）要素 + M2 推导量 + 交付层标签 → 裁量训练表。

### 5.1 已经在 CAIL 上做过的训练：锚点 A2 与 M1 探针 🟡

**训练的是什么**：刑事量刑预测，相当于 **M4 裁量模型的雏形**，而且是在刑事数据上。**不是训练要素抽取模型 M1**：M1 在里面只是"特征提取器"，用的是零样本输出，本身没有被训练。

**任务**：读 CAIL2018 刑事判决的"经审理查明"事实，预测刑期落在 10 个区间中的哪一个。区间照搬 PLJP 的定义（其他、≤6 个月、6–9、9–12、1–2 年、2–3、3–5、5–7、7–10、10 年以上），这样才能和 MSR² 的 46.2% 比较。

**数据与字段**：

| 层次 | 字段 |
|---|---|
| CAIL 原始记录 | `fact`（事实）；`meta`：`accusation`（罪名）、`relevant_articles`（法条）、`term_of_imprisonment`（刑期月数、死刑、无期）、`punish_of_money`（罚金）、`criminals`（被告人） |
| 我们整理后的样本 | `id`（事实文本哈希，用来去重）、`fact`、`charge`（赌博或开设赌场）、`months`（刑期月数）、`cls`（10 区间之一，**标签**）、`fine`、`criminals` |
| 划分 | 去掉 27 件重复后共 4,133 件，按 8:1:1 划分：训练 3,306、验证 413、测试 414（测试集封存未用）；后续改为在训练 + 验证上做 5×5 重复交叉验证 |
| 文本特征 | 事实的字符 1–3 元 TF-IDF（约 20 万维） |
| 要素特征（M1 探针） | M1 零样本抽出的 37 个字段 → 约 60 列：枚举字段独热编码，金额取区间中点再取 log，人数、次数取 log，布尔值记 0/1，**没抽到记 NaN**；另加罪名、事实长度 |

**两轮实验**：

| 轮次 | 模型 | 结果（区间准确率） |
|---|---|---|
| 第一轮（单一验证集 413 件） | TF-IDF + 线性 SVM / 逻辑回归（基线 B4） | 44.55（多数类 40 左右） |
| 第一轮 | 正则粗抽 17 个要素 + 梯度提升树 | 40.92（与多数类持平） |
| 第二轮（M1 探针，1,613 件，5×5 交叉验证） | 多数类 | 41.60 |
| 第二轮 | 文本 TF-IDF + 逻辑回归 | 41.77 ± 1.92 |
| 第二轮 | **M1 要素 + 强正则梯度提升树** | **42.66 ± 1.82**（比文本高 0.89，p = 0.24，**不显著**） |
| 第二轮 | 有序回归（预测 log 月数再映射回区间） | 26–28（损失函数与指标不匹配，见 M1 笔记 §8） |

**得出的三条结论**：
1. **CAIL 的信息上限很低**：19% 的案件既无金额也无情节，刑期却从 1 到 27 个月不等，"先抽要素"的优势体现不出来。这不能推广到行政案件。
2. **小验证集会让结论反过来**：单一验证集上要素显著差于文本，换成 25 折交叉验证后反而略好。所以门禁 A2 改成了交叉验证 + 修正 t 检验。
3. **损失函数要和指标匹配**：M4 应该先预测整个分布，再按指标选决策（区间准确率取众数，绝对误差取中位数）。

**和行政训练集的关系**：这一轮相当于在刑事数据上搭了一张"D2 样式"的表，但要素特征来自未经验证的零样本抽取（不是金标）。刑事罚则与治安罚则不同，所以 CAIL 只作为锚点 A2 和 M4 专家 A 的方向先验，不与行政案例混合训练。A2 是否改为不阻断的参考指标，仍待决定（§8 第 11 项）。

### 10.2 试标改为"双模型背对背标注" ✅（偏离日志 D-001）

**做法**：
1. 标注员 A = DeepSeek-V4.1-Flash（API），标注员 B = qwen3.5:9b（本机，受限解码）。两者来自不同厂商、规模不同，"同错同对"的可能性比"同一个模型跑两次"小得多；同一模型跑两次只能测出采样随机性，测不出指南是否清楚。
2. 两者拿到**同一份标注指南、同一段提示**，输入是 `text_party` + `text_facts`，互不可见。
3. 逐字段比较，算一致性；分歧逐项归类为"指南歧义 / 模型读错 / 证据缺失"，凡是"指南歧义"都补进标注指南，最多修订两轮。

**一致性怎么算（Cohen's κ）**：
- κ = (实际一致率 − 碰巧一致率) ÷ (1 − 碰巧一致率)。"碰巧一致率"按两个标注员各自的取值比例算。
- 为什么不直接用一致率：假如 90% 的案件都是"参与赌博"，两个标注员即使闭着眼都猜"参与赌博"，也会有 0.9² + 0.1² = 82% 的碰巧一致。此时实际一致率 90% 只对应 κ = (0.90 − 0.82) ÷ (1 − 0.82) ≈ 0.44，并不算好。
- **只在至少一方给出非"未提及"的字段上计算**：抽头、前科这类字段，大多数案件两边都会填"未提及"。如果把这些也算进去，一致率会被抬得很高，却什么也说明不了（与 §4.5、[对齐清单](../05-research/data-requirements.md) §2 的"指标防空转"同理）。"未提及"的一致率另外单独报告。
- 门槛不变：分类字段 κ ≥ 0.80，数值字段完全一致率 ≥ 95%。

**它能证明什么、不能证明什么**：
- 能：标注指南和字段定义是否清楚到让两个不同模型得出相同结论；分歧集中在哪些字段（这正是试标"检验指南"的目的）；同时初步看到 B1 的抽取质量。
- 不能：人工标注员能否稳定执行指南；两个模型都错时，一致率照样会高。
- **不变的**：G1.2（金标 20% 双人标注）、"任何测试集只用金标"、"金标＝人工校正"。如果以后也想用模型代替人工做金标，是另一项更大的决定，会影响全部 P2–P5 门禁的效力，需要单独登记。

**运行前还需要**：DeepSeek API Key（§10.1）；启动本机 Ollama 跑标注员 B（按约定先征得你同意）；最好先完成 I-02（加 `text_party`），否则标注员只能读到事实段，年龄等字段会大量缺失。

## 9. 术语表（随讨论补充）

| 术语 | 含义 |
|---|---|
| Ω（合法输出空间） | 适用法律下所有合法的处罚组合；M4 的输出只能落在里面 |
| 从旧兼从轻 | 行政处罚法第三十七条：原则上适用行为时的法，新法更轻时适用新法 |
| 受限解码 | 大模型每生成一个词前，先屏蔽不符合 JSON 格式的词，保证输出一定能解析 |
| 共形预测 | 一种给区间加覆盖率保证的方法：例如保证 90% 的真实结果落在给出的区间里 |
| 分组（Mondrian）共形 | 按地域、档次分组分别标定，保证每组都接近 90%，而不只是整体平均 |
| 银标 / 金标 | 教师模型自动标的叫银标（只用于训练）；人工校正过的叫金标（才能用于测试） |
| 锚点 | 公开基准上的对照，证明方法本身不弱 |
| 冻结基线 | 版本固定的简单方法，引擎必须显著优于它们 |

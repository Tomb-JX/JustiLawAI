# JustiLawAI 阶段交接概览（草稿）

> 2026-10-28 · 面向第一次接手项目的成员。本文解释项目的组成、数据和请求怎样流动，以及当前做到哪里；具体规则、接口和最新进度以文末链接为准。

## 一、项目要解决什么问题

JustiLawAI 是面向赌博类行政案件的学生大创项目。项目希望把**案件事实、适用法律、地方裁量基准和历史执法情况**放到一条可追溯的处理链路中，辅助办案人员计算裁量范围、辅助审核人员检查已作出的处罚。网页另有通用的对话、智能体、知识库和工作流能力。

当前主要有两个服务方向：

- **裁量计算器**：决定作出前，根据已核实的事实，显示法律允许的处罚范围、地方档位、历史处理情况和待补查事实。
- **决定书审查**：决定作出后，从文书整理事实与实际处罚，对照法律范围、地方基准和历史情况，提示值得人工复核的偏离。

两者共用法律规则与裁量内核。系统提供辅助材料和复核线索，最终事实认定与处罚决定仍由人完成。面向公众解释“可能结果范围”的服务属于后续方向，尚非完成的独立产品。

## 二、全局架构：离线研究与在线服务在何处相接

```text
离线的数据与研究链路                     在线的产品与服务链路
处罚决定书等来源材料                     人工填写事实 / 笔录或决定书文本
          ↓                                          ↓
采集、去重、解析、质量检查                 网页工作台 → 后端接口
          ↓                                          ↓
数据湖：原文、统一记录、来源及批次         文本分段、要素抽取（需要时调用模型）
          ↓                                          ↓
要素整理、人工标注、规则核对、实验          人工确认结构化案件事实
          ↓                                          ↓
规范规则、统计分布、实务模型参数 ──────→ 法律定档 → 历史参照 → 结果及追溯记录
```

**离线链路**负责建立材料和研究产物。“数据湖”是研究用的文书、统一记录及来源清单；它不是网页会话库，也不是前端直接查询的在线数据库。原始文书和大量实验输出存放在代码仓库之外，仓库主要保存程序、规则与模型产物、配置和文档。

**在线链路**负责处理一次具体请求。用户填写事实，或提交文本让系统先生成事实草稿；后端使用经确认的结构化事实进行规则计算，再附上历史统计参照、依据和运行记录。在线服务使用已经装配的规则与模型参数，不会在每次请求时重新采集数据或训练模型。两条链路在“经过核对的规则、统计分布和模型参数进入服务”这一步相接；研究实验的结果不会自动成为产品结论。

## 三、仓库各部分的职责

| 位置 | 负责什么 | 怎样连接其他部分 |
|---|---|---|
| `justilaw-web/` | React 网页：聊天、智能体、知识库、模型、工作流和裁量工作台；显示表单、依据、结果及运行历史。 | 通过 `/api/v1` 请求后端，不直接读取研究数据湖。 |
| `justilaw-api/` | FastAPI 在线服务：提供接口、保存应用运行数据，组织模型调用与裁量计算。 | 接收网页请求，读取已装配的规则、统计和模型产物。 |
| `research/` | 离线采集、文书清洗、统一结构、要素整理、标注质检和评测。 | 为规则核对和模型研究提供材料；部分文本处理逻辑被在线服务复用。 |
| `docs/` | 需求、设计、接口契约、研究结论、算法规则和进度记录。 | 解释设计缘由，并记录当前口径与缺口。 |
| `Dockerfile`、`docker-compose.yml`、`launcher/`、`ops/` | 构建、单机运行与运维。 | 单机容器打包网页和 API，持久卷保存应用运行数据。 |

后端内部：`app/routers/` 接收请求；`app/model_gateway/` 统一接入已配置的大模型；`app/rag/`、`app/workflow/` 支撑通用知识库和工作流；`app/discretion/` 承担赌博案件的事实结构、法律规则、实务参照与追溯记录。会话、设置、知识库和裁量运行记录属于**应用运行数据**，与 `research/` 使用的**研究数据湖**用途不同。

通用聊天和工作流是产品基座；裁量计算器和决定书审查是重点建设的领域服务。它们共用网页、模型配置和后端基础设施，但裁量结论不是让聊天模型直接“猜一个处罚”。

## 四、一次裁量请求怎样得到结果

1. **取得事实**：案件要素是行为方式、地点、日期、赌资、人数及相关情节等结构化信息。用户可直接填写，也可由系统从笔录、叙述或决定书中抽取草稿。文本处理通过模型网关调用已配置模型，并保留可定位的原文证据；自动抽取的内容需由人确认，未知字段不能默认为已查明事实。
2. **确定法律边界**：规则内核结合行为和决定日期，判断适用的国家法律、法定处罚范围及修正情节。这里回答“法律允许什么”。
3. **应用地方基准**：在目前已录入的河北、江苏规则范围内，按辖区和案件要素确定档位与处罚种类。条件不足时保留候选并提示补查，不靠模型补造事实。
4. **提供历史参照**：系统另行展示历史处罚种类的统计分布和实务模型参照；档内金额或天数按法定幅度过滤后作统计展示。这些信息帮助理解实际执法差异，**不改变法律给出的边界和档位**。
5. **形成可复核输出**：规则结论、历史参照、缺失事实和偏离提示分开展示，同时保存条文、计算过程、数据口径、模型调用及运行记录，方便核查每一步的来源。

决定书审查在入口增加“解析实际处罚”，在出口增加“实际决定与规则及历史情况的对照”。超出法定空间、偏离地方基准、与历史实务差距较大，是不同性质的提示；都需要人复核文书是否遗漏事实或情节。

## 五、页面、接口与运行方式怎样配合

裁量工作台已接入网页：可以录入事实、处理文书、查看结果和依据、查看运行历史；模型管理页面可配置文本处理使用的模型。人工事实评估可直接返回结果；文书分段、要素抽取和决定书审查采用“提交任务 → 获取运行编号 → 查询状态与结果”的方式。通用对话、知识库和工作流走各自接口，模型调用共用平台网关。

单机部署时，构建过程把网页与 API 放进同一镜像，浏览器访问同一服务；模型服务可由宿主机提供。会话、知识库、设置和裁量运行记录保存在持久化应用数据目录。研究材料及数据湖另行管理，不随代码仓库或应用数据卷一并交付。

## 六、目前进度与交接边界

- **数据链路已运行**：本次核对的数据湖有 14,257 条记录、12,031 份文书，涉及 19 批材料。这是材料规模，不表示每份都能训练、每个字段都已人工核定，或新一轮数据已经通过交付审核。
- **裁量主链路已有可运行实现**：国家层法律判断、河北和江苏地方基准、历史参照、偏离检查与追溯记录已接入后端。规则原文覆盖、更多省份、新法时期和更多人群仍需核对与验证。
- **工作台代码已并入共用代码并推送远端**：前端生产构建及裁量后端测试通过；真实模型调用和完整浏览器流程仍待联调。代码并入不等于产品验收完成。
- **研究与发布要分开看**：现有开发用标签、实验报告和待放行数据，不能直接算作已验收产品数据。实务模型仅在特定省份、行为类型和时期有检验依据，不能超范围外推。完整类案检索及更完善的偏离预警仍是后续工作。

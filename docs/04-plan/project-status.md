# 项目现状总览与数据流水线规范化方案

> 2026-10-16 15:00 快照 · 引擎工作流整理 · **共享文件**（分工文档 §2）
> 目的：一页看清"谁在做什么、产物在哪、卡在哪"，并提出让数据从采集到交付引擎可复现、可对账的规范。
> 所有数字均为本快照时实测；之后以本文 §6 规定的登记表为准，不再在各文档里各记一份。

## 0. 一页结论

1. **数据第一次走通了"采集 → 解析 → 脱敏 → 交付"全程**：发现层 14:43 产出首批交付文件，15:00 前又重建一次（harvest-0.4）。现在主文件 **881 件**，涉及 407 个事件，已脱敏，隐私扫描硬命中为 0；另有只有结果的条目 678 件。
2. **但离金标还差两步**：没有教师模型银标，也没有人工校正。而且交付数据在三项指标上不达标：
   - 信息完整度 40%（354/881），要求 ≥ 80%；
   - 新法案件 18 件，要求 ≥ 50；
   - 不予处罚 2 件，这一类必须单独达标。
3. **乱的根源不在"做得少"，在"没有统一的约定"**，具体是六件事（§3）：
   - 会话和目录归属不清；
   - 产物同名互相覆盖、原地重建、没有版本；
   - 三套解析器各出各的格式；
   - 文档多、数字反复更正；
   - 法宝积分没有统一记账；
   - 法宝作业台和合规红线有冲突，需要人来定。
4. **规范化方案**（§4–§6）：
   - 数据分六层，每层规定目录和命名；
   - 所有来源先统一成同一种中间格式，再走同一条脱敏和交付构建；
   - 交付按版本发布、不再覆盖；
   - 用一张登记表记录所有产物；
   - 引擎对每个版本自动验收并出报告。

## 3. 乱在哪里（具体问题）

1. **归属不清**：
   - 四个会话，只登记了三个；
   - 脱敏与交付本属数据链路，实际由发现层产出；
   - 主检出会话同时写数据链路的 `collect/` 和引擎的 `docs/05-research/`、`research/eval/`。
   - 结果是同一件事有两三份文档、两三种实现。
2. **产物会互相覆盖，也没有版本**：
   - `pkulaw_ingest.py docs` 的默认输出目录就是 `admin/`，写出的 `admin_outcomes_only.jsonl` 和 `SHA256SUMS` **与发现层的交付文件同名**，运行一次就会覆盖对方；
   - 法宝解析的 99 件 L1 产物现已不在数据目录；
   - 交付文件原地重建，旧版本不保留，引擎用过哪一版无从复现。
3. **没有统一的中间格式**：网页、法宝、裁判文书三套解析器各出一种形状，[数据链路全景](../05-research/data-flow.md) §4 已列出四处不一致：
   - `quality` 和 `completeness` 两种写法并存；
   - 内部字段混进交付；
   - 部分来源缺 `region`；
   - `event_key` 和 `event_id` 两种写法并存。
   
   脱敏、去重、区划只在网页这条线实现了，法宝和裁判文书的数据还没有接入。
4. **文档太多，数字反复更正**：
   - 与数据相关的文档约 17 份（不含协作记录和本文）；
   - 交付量多次更正（194 → 341；1,242 → 600）；
   - "法宝执法库只有摘要"的结论先下后改；
   - 积分余额在不同文档里分别写着 9,700、8,300、6,250；
   - `data-flow.md` 和 `data-requirements.md` 还写着"D1–D5 未拍板"，实际已经定了；
   - 提交 fafd078 把"指导老师确认合规""绑定学院订阅"等人工待办从三份文档里删掉了，**这些外部依赖现在在任何地方都看不到了**。
5. **法宝积分没有统一记账**：余额已从 10,000 降到 6,250。引擎花了 1,700 分（台账记 1,400 分，另 300 分花在调用层建好之前），其余 2,050 分由作业台和 worklist 花掉，没有台账。剩余积分 2026-11-15 过期。
6. **合规红线冲突**：[法宝作战手册](./pkulaw-playbook.md)的红线是"不对 pkulaw 写自动抓取脚本、不绕每日导出限额"。作业台的设计却包括：用浏览器自动检索、"零配额"逐条打开详情页抓正文、自动下载（有上限）。设计文档认为"真浏览器、人类节奏"就是合规的。**两种说法矛盾，需要人来定**，不应由某个会话自行决定。

## 4. 规范化方案一：数据分层与目录契约

所有来源走同一套分层，每层只有一个写入方，**写过的不改，只追加新批次或新版本**：

| 层 | 目录 | 内容 | 写入方 | 规则 |
|---|---|---|---|---|
| L0 原始 | `raw/<来源>/<批次>/` | 网页原文、导出的 doc/xls、采购文件 | 各来源负责人 | 只读归档；批次名 `YYYYMMDD-说明` |
| L1 解析 | `parsed/<来源>/<批次>/records.jsonl` | **统一中间格式**（方案二），未脱敏 | 各来源负责人 | 一个批次一个文件；附 `stats.json` |
| L2 构建 | `build/<版本>/` | 合并所有来源的 L1 → 脱敏 → 隐私扫描 → 去重 → 事件分组 → 分级 | **一个构建脚本、一个负责方** | 版本号如 `2026-10-16.r2`，记录输入了哪些批次 |
| L3 交付 | `delivery/<版本>/` | `admin_cases.schema-1.0.0.jsonl`、`admin_outcomes_only.jsonl`、`SHA256SUMS`、`build_stats.json`、`r6_report.json`、`DATACARD.md` | 构建脚本 | **不覆盖**；`delivery/LATEST` 指向当前版本 |
| L4 验收 | `delivery/<版本>/acceptance.json` | 引擎按规格 §4 自动验收的结果 | 引擎 | 不合格的版本不进入标注 |
| L5 标注与划分 | `labels/<schema 版本>/`、`splits/<版本>/` | 银标、金标、训练/验证/测试划分（只记 id） | 引擎 + 法律组 | 测试集封存按门禁 §7 |

各工作流的私有目录（`engine/`、`discover/` 缓存、`browser-profile/`）不属于这六层，其他工作流不读。确有需要的，通过 L1 或 L3 交接。

## 5. 规范化方案二：统一中间格式与唯一构建

- **中间格式**（L1）= 数据交付规格 v0.2 的字段 + 一个 `quality` 对象。`quality` 包含：来源形态、分级（L1 金标候选 / L2 只有结果 / L3 范围外 / L4 待核）、是否在范围内、完整度、解析警告。还要带一个 `event_key`，用"处罚机关 + 事实段首个日期 + 金额"生成。
  - 三套解析器各自把输出转成这一格式：`harvest/parse.py`、`collect/pkulaw_ingest.py`、`collect/ingest_wenshu.py`。
  - 引擎提供一个格式校验函数，三方共用。
- **唯一构建**（L2）：发现层现有的脱敏、隐私扫描、去重、区划实现，升级为**所有来源共用**的交付构建。法宝和裁判文书的数据只需交出 L1 文件，不再各写一套脱敏。
- **跨来源去重**：同一份处罚决定书可能同时出现在公开网页和法宝里。构建时按 `doc_no_hash` 和近重复检测合并，保留信息最全的那一份。

## 6. 规范化方案三：登记、验收与记账

1. **数据登记表** `$JUSTILAW_DATA_DIR/REGISTRY.csv`，每个构建和导入脚本自动追加一行：层、路径、条数、SHA-256、产出工作流、管线版本、时间、状态（现行 / 已取代）。**各文档引用数字时只引登记表里的版本号**，不再手抄。
2. **引擎自动验收**：`research/eval/accept_delivery.py`，按规格 §4 逐项检查，输出 `acceptance.json` 和一页摘要；不合格项按记录 id 列出，退回构建方。
3. **积分统一记账**：所有法宝 MCP 调用都走 `research/eval/pkulaw_mcp` 的调用层（自带台账，按工作流记账），或者至少每天在协作记录里报一次花费。剩余 6,250 分先定分配，再花。
4. **文档收敛**：
   - 本文作为唯一入口；
   - `data-pipeline-status.md` 和 `data-flow.md` 合并成一份现状文档；
   - 已过时的文档在文档地图里标"已取代"；
   - 人工决策和外部依赖统一列在本文 §7，不从文档里删除。

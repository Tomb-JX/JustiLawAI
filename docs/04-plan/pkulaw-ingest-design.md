# 北大法宝（渠道 C）数据化链路设计

> 版本 v0.2 · 2026-10-16 · 依据 2026-10-16 实样（两份目录列表 .xls：行政执法库 + 司法案例库；处罚决定书 .doc 两份）
> 配套：[渠道 C 作战手册](./pkulaw-playbook.md)（检索式 / 导出 SOP / 侦察）· [行政案例数据交付规格](../05-research/data-spec.md)（**本文所有"要求"均以该规格为准**）· [文本处理规范](./text-processing-spec.md)（D1–D5 待拍板项）· [数据收集计划](./data-collection.md)
> 代码：`research/discretion/collect/pkulaw_ingest.py`（解析）+ `pkulaw_xls2csv.ps1`（xls→CSV）+ `tests/test_pkulaw_ingest.py`

## 0. 结论先说

1. **法宝给的是"索引 + 标签"，不是"语料"。** 本次实样（行政执法库的处罚决定书公示）**只有 7 行字段，没有违法事实、没有行为日期**——决定处罚的信息不在文本里，和金标要求的"事实段"完全对不上。这类记录按 D6 只能进**结果-only 层**（分布校准、省份普查、T-time 计数），**不能进金标、不能当模型输入**。
2. **真正稀缺的是"含事实"的文书**：行政判决书、复议决定书、政府网站原文。司法案例库的**目录表已实测**（案由/法院/案号/审结日期齐全，更新到 2026 年），但**判决书正文仍未取得**——三天窗口第一件事就是导一份判决书正文，确认是否含"经审理查明"事实段。含则可当语料主力，不含则法宝只能回到"索引 + 标签"的角色。
3. **法宝有两件别人给不了的东西**：① 结构化的**法律版本**（"…(2012修正)第70条" / "(2025修订)第82条"）——没有行为日期也能按法条版本分片，直接定位 T-time（2026 新法案件）；② **规模**（2026 年个人赌博 8,292 条），可以按省普查，**定量回答"目标省选哪个"**这个 P1 卡点。
4. **司法案例库检索必须以"案由"筛，不能只靠全文词**：实测"全文：赌博"命中的 7 条里 3 条是民间借贷/建设工程纠纷（43% 噪声），只有 4 条是真赌博案。
5. 解析链路已落地并跑通（12 项单测 + 两种目录形态与文书端到端实样验证）：目录 xls → 工作清单（哪些还没下全文）；文书 → 规格 JSONL（自动分级：有事实 → `admin_cases.jsonl`，无事实 → `admin_outcomes_only.jsonl`）。
6. **与渠道体系的关系**：本文对应[数据收集计划](./data-collection.md) v0.4 的 **C2（网页人工导出）**；C1（MCP 目录）用途之一"机关 + 文号反查原发布机关公示页取全文"正是把结果-only 记录**升级成含事实案例**的通道（反查到原文页后交发现层收割）。v0.4 写的是 C2"待学院订阅绑定后启用"——**本次三天窗口的授权性质需先确认**（学院订阅绑定 / 试用额度 / 个人账户），若属个人账户则先不与 v0.4 的红线冲突再批量导。

## 1. 实样解剖（两种导出形态到底给了什么）

### 1.1 目录列表 `.xls`（行政执法库："北大法宝V6-行政执法-行政执法字段表单"）

- 形态：BIFF8 二进制（**不是** HTML 伪装）。读取用 **xlrd 直读**（`pip install xlrd`，纯 Python）；
  `pkulaw_xls2csv.ps1`（Excel COM → UTF-8 CSV）只作没有 xlrd 时的兜底——COM 在无人值守时会因受保护视图或残留进程卡死（本次实测卡死过一次，孤儿 EXCEL.EXE 占 468MB）。
- 结构：第 1 行子库名；第 2 行**搜索条件 + 下载时间**（数据卡 G1.4 要的溯源信息，必须留住）；第 3 行字段名；其后数据行；末尾版权与二维码页脚（按标记截断，不能当数据行）。
- 字段（11 列）：序号 / 标题 / 执法机关 / 发文案号 / 公布日期 / 行政相对人 / 执法依据 / 处罚种类 / 执法地域 / 原文链接 / **罚没总金额（万元）**。
- 实测（本次 8 行）：`罚没总金额` 0.03 万 = 300 元（罚款档）；拘留档为 0；`执法依据` 带版本字样；`序号` 形如 `_1`（不可靠，不作主键）；`行政相对人` 在本批为空（doc 里有）。
- 解析器**不写死列名**：表头行按"已知列名出现 ≥3 个"识别，子库新增列不需要改代码（行政执法库与司法案例库两套列共用一套解析）。

### 1.2 文书 `.doc`（处罚决定书公示）

- 形态：真 OLE2 二进制；`antiword` 取文本完好（表格保成 `|字段|值|` 行），失败可退 Word COM。
- 内容 = 元数据块 10 项（主题分类/处罚种类/行政相对人/执法级别/执法机关/执法地域/公布日期/发文案号/罚没情况/执法依据）+ 决定表 7 行（文号/被处罚对象/处罚事由/处罚依据/处罚结果/处罚决定日期/处罚机关）+ 页脚（版权 + 原文链接）。
- **法宝引证码（`FBM-CLI.ALE.47644244`）在文件名里**——这是最稳的主键，比文号可靠（同案多人文号不同，同一文号可能重发）。
- 人名**已被法宝遮挡**（陈\*英、黄\*鸣）；仍需 R6 扫描确认无身份证、住址、出生日期。

### 1.3 目录列表 `.xls`（司法案例库，另一套列——2026-10-16 第二份实样）

- 字段 9 列：序号 / 标题 / **审理程序 / 案由 / 文书类型 / 审理法院 / 案件字号 / 审结日期 / 省份**（与行政执法库 11 列几乎不重叠）。
- `案由` 是层级串：`刑事>妨害社会管理秩序罪>扰乱公共秩序罪>开设赌场罪★;`；`省份` 列实际填的是**法院全名**（"湖南省溆浦县人民法院"），要按省名规范化。
- **实测噪声率 3/7 ≈ 43%**：检索式是"全 文：赌博"，命中的 7 条里 3 条是民间借贷、建设工程合同纠纷（只是判决书里提到"赌博"），只有 4 条是真赌博案（开设赌场罪 3、赌博罪 1）。
  → **司法案例库必须以"案由"筛（治安管理处罚 / 赌博罪 / 开设赌场罪），不能只靠全文词**；这条与[裁判文书采购需求](../05-research/wenshu-retrieval-plan.md) v0.3 的结论一致。
- 全部为 2026 年审结判决书 → 司法案例库更新到 2026 年（T-time 的时间窗可用）。
- 目录表里有 `案件字号`（如 `(2026)湘1224刑初264号`）→ 省份/法院层级可由案号代字复核，也用作判决书主键（与 wenshu 采购同规则）。

## 3. 真正需要的形式与内容（需求侧，不拟合样本形式）

**目标不是"把法导出转成 JSON"，而是凑齐四件套：** 事实段（`text_facts`）+ 行为日期 + 处罚结果精确标签 + 情节认定。四件套缺哪个，那条记录就只能降级使用。

三类子库分工（法宝内部也是三条不同的数据线，别混为一谈）：

| 子库 | 给什么 | 在项目里的位置 | 优先级 |
|---|---|---|---|
| **行政执法库**（本次实样） | 处罚结果 + 元数据 + 法律版本，**无事实** | **结果-only 层**（D6）：分布校准、省份普查、T-time 计数、行刑衔接统计；不进金标 | 全量导目录（便宜），正文按需 |
| **司法案例库-行政**（R3） | 判决书：法院查明事实 + 原处罚 + 审查意见 | 可能的**语料主力**（若含事实段） | **三天窗口第一优先（先试检）** |
| 司法案例库-复议（R2） | 复议决定：事实 + 原处罚 + 复议结论 | 语料 + T-admin 构成（≤50% 约束） | 第二优先（先试检是否收录） |
| 法律法规库 / 地方法规库（R4/R5） | 规范原文（含省级裁量基准） | 清 G0.1 待核验；法律组录 YAML，不走案例管线 | 顺手导 |

**导出形式的选择原则**（形式服从内容）：
- **每个检索式先导"目录列表 xls"**——它是索引 + 元数据 + 结果标签，几乎不耗时间，且本身就是有用的结果-only 数据。
- 正文按目录挑着导。**先试检 1 份"纯文本"导出**：若纯文本已含元数据块与决定表，后续优先导纯文本（省掉 .doc 解析与 antiword 依赖）；PDF 只在扫描件场景用（`harvest/ocr.py` 已有 OCR）。
- 解析器不绑定文件形式：`doc_to_text()` 支持 antiword / Word COM / docx / txt 四种取文本方式，解析按"标签 → 值"抽取，换排版只影响抽取规则，不影响字段映射与产出。

## 4. 数据化链路

```
法宝网页（人工检索/勾选/官方导出，不写抓取脚本）
   │  目录列表 .xls ──pkulaw_xls2csv.ps1(Excel COM)──→ catalog_*.csv
   │  文书 .doc/.docx/.txt ──→ inbox/pkulaw/<检索式>-<日期>/
   │                                    │
   │            import_manual.py（入台账 channel=C，算哈希，分配 id）
   ▼                                    ▼
pkulaw_ingest.py catalog            pkulaw_ingest.py docs
   → worklist.csv（工作清单 + 已下全文标记）  → 按文号 join 工作清单、按 SHA-256 回填台账 id
   → catalog.stats.json（按法条/省/年份/处罚种类） → admin_cases.jsonl（有事实=金标候选）
   ↑ 决定下一批下什么                        → admin_outcomes_only.jsonl（无事实=结果-only，D6）
                                            → SHA256SUMS + pkulaw_ingest.stats.json
                                                    │
                                    脱敏（D1–D5 拍板后）+ R6 扫描 → 交付引擎
```

命令（仓库根目录）：

```bash
# 依赖：pip install xlrd（读 .xls）；没有 xlrd 的机器先用 pkulaw_xls2csv.ps1 转 CSV，再喂 --xls 指向 CSV
python research/discretion/collect/pkulaw_ingest.py catalog \
    --xls "inbox/pkulaw/R1/【北大法宝】目录列表.xls" --out $JUSTILAW_DATA_DIR/pkulaw/R1
python research/discretion/collect/pkulaw_ingest.py docs --docs inbox/pkulaw/R1/docs \
    --worklist $JUSTILAW_DATA_DIR/pkulaw/R1/worklist.csv --out $JUSTILAW_DATA_DIR/admin
```

**主键与去重**：法宝引证码（文件名）为主键；无引证码时退文号。同一 URL（32 位哈希）重复下载视为同一条。
**事件分组**（门禁 §7 防泄漏）：同机关 + 同决定日期 + 文号连号多为同一次查处（实样 00289/00290 即两人同一次），脚本输出 `event_hint`（机关+决定日+文号尾号）供划分时聚合。
**质量门**：脚本统计 `outcome_only` 占比、`parse_warnings`（facts_missing / outcome_not_parsed / articles_not_parsed / fine_mismatch / not_in_manifest），交付前人工看一遍。

## 5. 三天窗口的检索与导出计划

> 前提：按[作战手册](./pkulaw-playbook.md) §2 的 R1–R5；账号仍未绑定学院订阅（个人账户），命中数待绑定后复测。

| 时段 | 做什么 | 为什么 |
|---|---|---|
| **第 1 步（最优先，约 1 小时）** | **导一份行政判决书正文**（司法案例库 → 选一条治安管理处罚案由的判决 → Word / 纯文本 各 1 份），比对是否含"经审理查明"事实段、"原处罚"与"审查意见" | 决定三天怎么花：含事实 → 判决书是语料主力，全力导；不含 → 全力走"索引 + 标签" |
| 第 2 步（半天） | **省域普查**：R1（行政执法库）按"执法地域"分省导目录 xls；R3（司法案例库）按"案由=治安管理处罚"导目录 xls | 定量回答数据收集计划 §2 的**目标省**待决策项（当前公开网页路线的省覆盖：山西 0、上海 0、湖南 15、云南 43、安徽 46、浙江 30） |
| 第 3 步（1 天） | **R3 行政判决正文**：案由"治安管理处罚"（**按案由，不按全文**）+ 需要时叠加全文"赌博" | 事实语料；实测全文检索噪声 43% |
| 第 4 步（半天） | **R2 复议决定书**试检 + 导出 | 含事实 + 复议结论；T-admin 构成 |
| 第 5 步（半天） | **新法分片**：`执法依据=2025修订/第82条` 的目录（T-time ≥50 件的来源）+ `不予处罚`（文号含"不决字"，MCP 建议） | G1.1 T-time；G3.2 不予处罚类**目前全网 0 件**，是硬缺口 |
| 第 6 步（收尾） | R4/R5 规范文件（法律组）+ 补漏；记录每条检索式的命中数/导出数/日期（数据卡） | G0.1 待核验清零；G1.4 数据卡 |

**额度纪律**：每批导出前记 `检索式 + 命中数 + 拟导出数`；导出后目录 xls 与正文文件数核对一致；导出文本**不二次分发**（手册 §5）。

## 7. 风险与合规

- **二次分发**：导出文本只存仓库外 `$JUSTILAW_DATA_DIR`，仓库只提交脚本与台账哈希（手册 §5）。
- **个人账户**：当前导出用的是免费个人账户，条款与额度都不是学院级；绑定前不做批量导出。
- **结果-only 层不得混入金标**：脚本按事实段自动分流，`admin_outcomes_only.jsonl` 与 `admin_cases.jsonl` 分开落盘；引擎侧按 D6 只用于分布与计数。
- **人名遮挡不等于脱敏完成**：法宝已遮挡姓名，但身份证、住址、出生日期须 R6 扫描确认；`deidentified` 在脱敏 SOP 执行前一律 false。

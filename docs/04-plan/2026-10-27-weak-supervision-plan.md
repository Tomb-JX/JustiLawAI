> **⛔ 2026-10-28 已停止**：binding-v2 整线停止归档（核心模型 M4 不消费绑定、弱监督与配对解码两条路线均未过止损线），见 [binding-v2 停止与归档](../05-research/2026-10-28-binding-v2-closure.md)。本文仅作历史记录。

## 0. 为什么换路线

10-27 写的两套规则（现场口径 `onsite_caliber.py`、个人归属 `personal_attribution.py`）证明了一件事：问题的结构是“同一小句里的 人名—连接词—金额”加“金额的口径”。个人赌资规则在 T4 上 121/123，现场赌资“判未提及”206/207。

但规则本身不是可持续的方案，原因有三：
- 约 20 组关键词里不少是看着单条错例加的（面值、替代、主板9块、均摊、流水……）；
- H3 上出现过一次过拟合，只按 dev 调完后从 15/16 退到 13/16；
- 现场赌资的填值部分在 T4 上不达标，只有 88%。

本计划把规则从“判官”降为“标注员”：
- 规则只给大量无标注文书打带噪声的标签；
- 由统计模型估计每条规则的可靠度并合成软标签；
- 再训练一个只看原文的编码器模型去学这种结构；
- 最后在全新封存集上、按事先写好的判据检验一次。

### 人名模型映射为什么一直没做（核查结论）
规划过三次，三次都没落地：

| 时间 | 规划 | 结局 |
|---|---|---|
| 10-17 | 解析层 v2：“人名识别是 NER 任务，规则只能覆盖列举过的语境”，计划正则 → 模型 NER | 当天用户取消脱敏，人名 NER 跟着脱敏一起“退出主管线”。可要素归属同样需要找人，这一需求没人接手 |
| 10-26 | 语义结构接入设计：“人物提及＋共指（ownership.py 规则提案 → 后续可由 NER 替换）” | X0 已在隔离环境装好 HanLP/LTP，3,051 段文本的 NER 结果已缓存，报告也写了“NER 把脱敏名识别为人名”。但 X1 的语义依存探针没过门槛（0.58 < 0.6），结论写成“HanLP/LTP 保留为离线工具，不进入生产链路”：NER 被连带丢掉，从没单独评估过 |
| 10-26 | 归属实验：“修正人名识别边界前后无差别，瓶颈不在找人” | 这个对比只在“已被规则找到的人”上做，漏掉的人根本不进候选，结论有选择偏差。人名层因此被降了优先级 |

另一个原因是许可证：设计要求“生产路径不依赖非商用模型”，HanLP/LTP 是 NC 许可。按用户 10-17 的约定，研究期可以用 NC 模型；产品化路线本来就是自训编码器，NER 只作教师。

结果是 `ownership.person_mentions` 一直是正则加补丁（PLACE_NEXT、NOT_GIVEN、PERSON_PREV 等），正是 10-17 文档点名要避免的“打地鼠”。

用现成缓存实测（921 段有缓存的事实文本）：
- HanLP 与 LTP 都认作人名的有 1,138 处，其中正则漏掉 184 处（16%）。漏掉的主要是“×”遮蔽（杨××、王××，正则的遮蔽字符里没有 ×）和不遮蔽的全名（贺春香、程兵、胡正望）；
- 正则多出、两个 NER 都不认的有 79 处，如“方式”“金额***”“张封顶”“张扑克”“程中”。

所以阶段 1a 不是新研究，而是把 10-26 已经做出来的 NER 结果接上去。

### 携带额与剩余额：按赌资的法定定义统一
两高《关于办理赌博刑事案件具体应用法律若干问题的解释》（2005）第八条：赌资是“用作赌注的款物、换取筹码的款物和通过赌博赢取的款物”。据此：
- **个人赌资 = 投入（携带）额 + 赢取额**；输掉的部分仍算投入；
- 同时写了携带额和查获时持有额时，取两者较大的那个：赢了则持有额 = 携带 + 赢取，输了则取携带额；
- 只写了其中一个时，取写出的那个；不由我们推算。

复核我之前说“参照口径不一致”的 11 个案例：10 个与上述定义一致，例如：
- 携带110、赢15、持有125 → 125；携带600、输60、剩540 → 600；
- 携带1235、输1000、扣235 → 1235；携带1000 筹码、赢230、查获1230 → 1230。

唯一例外是“共输775元，剩余赌资225元”取了 775，按定义应为 1000，但原文没写投入额，需要推算。所以我在《个人赌资归属规则》报告里写的“参照没有一致口径”是错的，已更正：参照基本一致，是规则没按定义处理。

补记：这条定义其实早已写在 dev/T4 审核用的 GUIDE-ADDENDUM 第 1 条（10-27 写定，在任何两轮比对之前），所以参照才是一致的。F5 直接沿用该补充条款，不另加条款；它也作为一个标注函数的语义（见 §4）。

## 4. 阶段 2：标注函数（LF）库

把现有规则和现有模型都拆成“只投票或弃权”的小函数，每个函数只代表一种语言现象：

| 组 | 例 | 来源 |
|---|---|---|
| 归属·点名 | LF_名字+连接词+赌资；LF_在X身上/从X处查获；LF_列表中X赌资Y元 | personal_attribution 拆分 |
| 归属·未点名 | LF_其个人赌资；LF_查获时身上有赌资；LF_共计充值 | 同上 |
| 归属·否定 | LF_他人点名（遮蔽/全名）；LF_每局/单次/封顶；LF_罚款句 | 同上 |
| 口径 | LF_合计标记；LF_其中领起的分项；LF_共同/无主；LF_人均/均摊；LF_输了/流水；LF_硬币枚数；LF_抽头 | onsite_caliber 拆分 |
| 结构 | LF_金额前最近人名距离；LF_句法主语（依存分析的主语是否为该人） | 新写（通用结构，不是词表） |
| 现有模型 | LF_frozen_chain、LF_softmax 路线、LF_pair_roberta（v1） | binding-v1 已有 |
| LLM | LF_qwen3.8-flash、LF_deepseek-flash：对 U 池每条记录按审核指南逐字段给出答案，再映射到对和金额 | 已有调用基建；U 池全量或分层抽样 |
| 定义 | LF_赌资定义：个人赌资 = 投入 + 赢取，同时写了携带与持有时取较大值（§0.5） | 法定定义，不是词表 |

要求：
- 每个 LF 在 dev 上报覆盖率、准确率、冲突率，并写进 `LF-REPORT`。
- LF 数量不追求多，一种现象一个函数。不同组之间尽量不相关：除词表类外，必须有结构类和模型类，否则标签模型会把相关的同源错误当成多票一致。

## 5. 阶段 3：标签模型（把多张带噪声的票合成软标签）

**原理（学习笔记会单独写一份）**：每个 LF 都是一个不完美的标注员。标签模型（Dawid–Skene 或 Snorkel 的生成式标签模型）只看各 LF 在大量无标注数据上的“同意/不同意”模式，用 EM 算法同时估计两样东西：
- 每个 LF 有多可靠；
- 每个样本真实标签的概率。

它不需要金标，靠的是“多个大体独立的标注员互相印证”。

做法：
- 用开源的 Snorkel LabelModel（Apache-2.0），或自己写约 100 行的 Dawid–Skene EM，二选一，在 dev 上比较；
- 对已知相关的 LF 组（同源词表）声明相关结构，或合并成一票，防止重复计票；
- 检验：
  - 标签模型在 dev 和 H3 上的准确率与校准（ECE），只看汇总；
  - 对比“多数投票”和“最强单条规则”两个基线，标签模型必须优于二者，否则这一步没有意义，退回检查 LF 设计。
- 产出：U 上每个候选对、每个金额的软标签，以及覆盖率统计。

## 6. 阶段 4：终端模型（真正的“算法”部分）

- **架构**：在现有 `train_pair_encoder.py` 基础上扩展。中文 RoBERTa 加实体标记（[人:目标]…[/人]、[额]…[/额]），沿用 Zhou & Chen 的“标记起点向量”表示，增加两个头：
  - 归属头：人—金额对；
  - 口径头：金额本身，输入是只标金额的窗口。
- **训练**：
  - 用软标签做噪声感知损失，即对软标签做交叉熵，不取硬标签；
  - 类别加权；
  - 按事件做 5 折交叉验证，固定种子。
- **只学原文**：输入里不放任何 LF 结果（§1 第 5 条）。
- **泛化证据（关键指标）**：在 dev 上单独统计“所有规则都弃权的样本”上模型的准确率。这一块如果明显好于随机，才说明模型学到了规则以外的东西。如果模型只在规则命中的样本上好，就判定为只是复刻规则，不进入下一阶段。
- **阈值与弃权**：在 dev 和 H3 的交叉验证预测上，选能达到目标精度（填值 ≥ 97%）的最低阈值，写进判据文件后冻结。
- **对照组**（同一 F5 上一起报告）：
  1. v1.1 服务；
  2. 10-27 冻结规则；
  3. 标签模型直接输出；
  4. 终端模型；
  5. 终端模型 + 规则一致性门（两者一致才填）。
- **鲁棒性**：复用已有反事实套件（换名、删证据、他人改名、改标签），要求终端模型不比规则差。
- **算力**：本机 RTX 5060 8GB（10-27 已获准使用），在 `justilaw-nlp312` 环境训练。推理导出 ONNX，主环境用 CPU 跑，结果确定。
- **LLM 与评测同源的风险**：LLM 标签是最强的标注函数，F5 参照又有 LLM 参与，评测会偏乐观。对策有三：
  - F5 分歧由 Claude 仲裁；
  - 同时在 T4（纯 Claude 参照）上报告，作为交叉核对，只报告不做决定；
  - 单独报告终端模型与 LLM 标签“一起错”的比例。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| LF 都是词表类、彼此相关，标签模型过度自信 | 强制加入结构类和模型类 LF；声明相关组；与多数投票基线对比 |

# 代理试标运行复盘（2026-10-16 · 金标质检线）

> 触发：用户对运行反复中断、严重超时提出正式批评，并质问"50 篇的分片策略能否显著提高判断效果"。
> 本文是诚实复盘，按根因分类，不含辩解。结论先行：**分片在这个体量下对判断质量没有显著收益（中性偏负），当晚的主要时间损失来自三个可避免的设计错误和两个判断错误；提供商通道不稳是背景因素，但应对策略失当放大了它。**

## 2. 根因分类

### 外部因素（背景，非设计错误）
- qwen 账户欠费；bigmodel GLM 三种账户形态间歇 unknown/network_error；DeepSeek 前稳后抖。
- 判据：同账户本会话主通道全程正常 → 疑似工作流并发通道问题，非账户问题。

### 设计错误（我的，按严重度排序）
1. **仲裁用"共享上下文 FIFO 仲裁员"拓扑——选错了。** 37 个 ask 串行压在一个子代理上：单点卡死即全线停摆、上下文膨胀（1100 万 token）、结果被最后一个写盘环节整体绑架。仲裁判断依据是协议+逐字证据规则，不依赖"同一上下文的校准"，一致性收益是臆想的，可用性代价是灾难性的。正确拓扑：每条分歧记录一个**自包含、并行、各自落盘**的代理，单条失败只损失一条。
2. **用 LLM 代理做确定性序列化。** "把 JSON 数组转录成文件"是 `JSON.stringify`+文件系统就能精确完成的事，我却派了一个模型往返——既慢又引入提供商依赖。正确做法：要么每个仲裁 ask 自己 Write 自己的决定行，要么把决定切片用 `world.run("python",…)` 落盘（每片 <32K 命令行上限）。
3. **组合产物没有进运行内验证门。** 我校验了 A、B 原标，却没在校验 merge 的输出 `arbitrated.jsonl`——merge 脚本的 B 拷贝 bug 因此逃过工作流，直到本地复算才暴露。"最强校验决定退出"必须覆盖每一个组合产物。
4. **端到端冒烟缺了后半段。** 冒烟测了标注格式与写入，没把 仲裁→合并→装配 全链路在 3 件样本上跑一遍——合并 bug 本可当场抓获。
5. **通道切换没有硬规则。** 明知 DeepSeek 通道全绿（B 的 10 片全成），仍为"标注员 A 模型纯度"在同一故障提供商内试了两次 GLM，各赔 20-26 分钟。应该：连续 2 次提供商失败（≈5 分钟）立即跨提供商切换，预declare 备选顺序。

### 判断错误（我的）
6. **状态误报。** 把"19/36 已裁"读成"19/20、只剩一条"并告知用户——日志里明明写着"共 36 条案卷存在分歧字段"，我没有对账。
7. **等待策略过于被动。** 三处卡点各空转 20-30 分钟才干预，把"运行器会无限重试"当成了"运行器值得无限等"。

## 3. 直接回答：50 件该不该分片？

**不该这么细。分片对判断质量没有显著收益，在这个体量下是中性偏负的。**

- 数据体量：50 件全文合计约 4 万字 ≈ 4 万 token，单个模型一次上下文轻松读完。任务本身就小，重烧的 2400 万 token 几乎全是拓扑开销（20 个分片各自重读协议、仲裁员反复重读材料、失败重试），不是数据量。
- **质量上**，分片反而有害：每个分片各自重新"发明"判断口径，产生分片间不一致——本次 A 标注员内部（GLM 分片 vs v4-pro 补片）在孕产字段上自我矛盾、κ 被人为压到 0.419，正是分片口径漂移的实证。单上下文标注员对 50 件的口径会更一致。
- **要诚实补一句**：单上下文的"一致"部分来自共享盲区——它抬高 κ 但不一定更正确。κ 的真实质量杠杆是**协议清晰度**（本次真正起作用的是冒烟出的 11 条澄清），不是分片拓扑。
- 分片的正当理由只有两个：超过单上下文容量（几百件以上）、以及隔离爆炸半径。这两个在 50 件上都不成立。合粒度应是 **1 个标注员 = 1 个代理 = 全部 50 件**（最多拆 2×25），而不是 10×5。

## 4. 若重来的设计（同样的活，预计 20 分钟、零事故）

1. **标注**：2 个代理（A、B），各自单上下文顺序标注 50 件，每标完一件**自行 Write 一行**到自己的输出文件（原子落盘，无集中写盘环节）。
2. **仲裁**：36 个并行自包含小代理（每条分歧一份内联材料：协议要点+原文+A/B 值），各自写自己的决定行，互不依赖。
3. **合并与校验**：本地 `world.run` python 合并 → **立即校验合并产物** → 装配脚本。
4. **通道策略**：预声明备选顺序（当晚证据下 DeepSeek 优先）；连续 2 次失败即切换，不等运行器。
5. **端到端冒烟**：正式跑之前用 3 件样本把 标注→仲裁→合并→装配 全链路走通（合并 bug 会在这一步暴露）。

## 5. 保留有效的部分

- 协议先行 + 冒烟：8 处指南空白在正式运行前暴露并统一口径——这是本次质量真正的来源。
- 分片级缓存：6 次修订中已完成的标注全部零成本回放，省约 400 万 token。
- 确定性计算本地化：κ/一致率/证据命中全部可复算，κ 手算对照过。
- 冗余校验兜住了所有错误：交付前 0 错误、逐条证据可审计。

## 6. 规则沉淀（下次批量任务硬规则）

1. 编排复杂度必须由数据量证明，不由"模式可用"证明。<200 件的任务不用 fan-out。
2. LLM 只做判断，永不转录；一切确定性序列化走本地脚本。
3. 每个代理自己落盘自己的产物；禁止集中式大数组写盘。
4. 每个组合产物进运行内校验门；工作流"成功"不算数，本地复算才算数。
5. 提供商失败硬规则：连败 2 次≈5 分钟即跨提供商切换，预声明备选顺序。
6. 状态汇报必须对账（已settled ask 数 vs 任务总数），禁止凭单读数下结论。
